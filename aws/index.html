Groundhog Day for AI agents: Prompt caching patterns for using OpenAI models on Amazon Bedrock

  • Amazon Bedrock introduces prompt caching to reduce costs and improve responsiveness for AI agents by reusing previously processed prompt prefixes, addressing the “Groundhog Day” problem of repeatedly sending full context with each turn.
  • Caching can be implicit, where Bedrock automatically determines the reusable prefix, or explicit, where developers define breakpoints in the prompt to delineate the cached section using prompt_cache_key and prompt_cache_options (with mode set to "explicit" or "implicit" and a ttl for cache lifetime).
  • Combining implicit and explicit caching allows for a reusable starting point (tools and instructions) while letting Bedrock manage the growing conversational history automatically; explicit caching requires consistent serialization of instructions and tool lists, and is recommended for static content.
  • Prompt caching is available for GPT-6 Astra (v7 using the KEY = "support-agent:v7:gpt-6-astra" example), GPT-6.1 Sol and GPT-5.6 Luna and can be used with new tools added mid-session via the additional_tools input type, enabling reuse of existing cached content.

Multi-Turn Reinforcement Learning on Amazon SageMaker AI: A hands-on guide

Multi-Turn Reinforcement Learning on Amazon SageMaker AI: A Hands-on Guide

This blog post details how to use Amazon SageMaker AI’s Multi-Turn Reinforcement Learning (MTRL) capability to train language models for agentic tasks requiring sequential decision-making.

  • MTRL trains models using a reward signal received after an entire sequence of actions, unlike standard fine-tuning or single-turn RL. It works by having an agent hosted on Amazon Bedrock AgentCore (or custom infrastructure) interact with an environment, and provides a reward at the end of an episode.
  • The example uses the game Wordle to demonstrate the pipeline, showcasing training of the gpt-oss-20b model, improving its solve rate from 61% to 84% at default reasoning effort, and from 15% to 69% at low reasoning effort, for approximately $339 in training tokens.
  • The system utilizes a two-part architecture: SageMaker AI for the training job and policy model, and AgentCore for hosting the agent, environment, and reward function; communication happens via an AWS Lambda forwarder. Group Relative Policy Optimization (GRPO) and Low-Rank Adaptation (LoRA) are used to update the policy model.
  • Currently supported base models include Amazon Nova 2 Lite, GPT-OSS-20B, Gemma 4 31B (instruction-tuned), and Qwen 3.6 27B; pricing is based on prefill, sample, and train tokens, as well as AgentCore runtime costs.

Stop guessing auto scaling targets for TTS on Amazon SageMaker AI

  • This post details a method for automatically determining auto scaling targets for a text-to-speech (TTS) endpoint using Amazon SageMaker AI, specifically with the Kokoro-82M (82-million-parameter) model.
  • The approach replaces guesswork with two measured values: Q_max (maximum concurrency per instance before breaching SLO) and T_total (total scale-out time), deriving scale-in/out thresholds and cooldowns through arithmetic.
  • The methodology utilizes the ConcurrentRequestsPerModel metric native to Amazon SageMaker AI, avoiding the need for custom metric emission, and addresses the shortcomings of default auto scaling metrics for TTS due to its non-autoregressive nature.
  • Deployment is managed via AWS CDK stacks, ensuring a measured plan exists before auto scaling resources are created, and a command-line toolchain automates the measurement process – drift check, Q_max measurement, T_total measurement, and plan generation – with a focus on accurately determining scale-out parameters.
