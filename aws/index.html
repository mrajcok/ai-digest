Full Fine-Tuning (FFT) on SageMaker AI Serverless Model Customization

Amazon SageMaker AI Serverless Model Customization now supports Full Fine-Tuning (FFT), enabling superior model quality by updating all model parameters simultaneously, overcoming limitations of methods like LoRA.

  • FFT addresses the limitations of Low-Rank Adaptation (LoRA) by enabling full model parameter updates, improving performance on complex tasks with large datasets.
  • Experiments on a Qwen3-4B base model using the Magicoder-Evol-Instruct-110K dataset showed FFT achieved 90.0% LLM-as-Judge semantic correctness, outperforming LoRA as dataset scale increased.

How ArisGlobal scaled generative AI inference on Amazon Bedrock

ArisGlobal significantly reduced inference costs for their NavaX AI engine, built on Amazon Bedrock, by strategically utilizing prompt caching.

  • ArisGlobal initially faced increased costs as their shared prompt prefix grew 150% over six months with increased tenant onboarding, leading to a 200% rise in per-case inference costs.
  • They reversed the request order, caching the shared prompt prefix before the per-case document using Amazon Bedrock’s explicit cache checkpoints (using cachePoint with a default 5-minute TTL, or up to 1-hour TTL for select models like anthropic.claude-sonnet-4-5-20250929-v1:0).
  • This strategy resulted in 65% of input tokens being served from the cache, achieving approximately 50% lower effective input cost and 40% lower overall monthly inference spend (at >19 billion tokens/month) while onboarding 15% more tenants.
  • The key takeaway is to prioritize caching content with high reuse potential (the shared prefix) over larger, case-specific content (the document) to maximize cost savings with Amazon Bedrock.

Secure OAuth patterns for Snowflake Cortex AI through Amazon Bedrock AgentCore

Amazon Bedrock AgentCore now supports secure OAuth patterns for accessing Snowflake Cortex AI via the Snowflake-managed MCP server. The core capability is Amazon Bedrock AgentCore Identity, which acts as a credential broker for obtaining and refreshing OAuth tokens. Three configurations are supported: Snowflake OAuth (per-user, no external IdP), three-legged OAuth with a third-party IdP (SSO), and two-legged OAuth with a third-party IdP (shared service user).

  • AgentCore Gateway connects agents to external tools via the Model Context Protocol (MCP) and uses AgentCore Identity to manage OAuth tokens.
  • Snowflake OAuth uses the Authorization Code grant type directly with Snowflake, requiring users to authenticate directly with Snowflake for consent.
  • Three-legged OAuth utilizes a third-party IdP via the Authorization Code grant, leveraging IdP-issued JWTs with Snowflake’s External OAuth security integration.
  • Two-legged OAuth employs a shared service user and the client_credentials grant via a third-party IdP, suitable for machine-to-machine workloads without user interaction.

Govern and discover records with common metadata in AWS Agent Registry

AWS Agent Registry now supports custom metadata schemas, enabling organizations to define and enforce consistent key-value pairs for all records (agents, MCP servers, skills).

  • Administrators define schemas with field names, types (Text, Enum, URL, Boolean), allowed values, and required/optional status.

  • The solution utilizes three strategies to handle large JSON payloads (up to 20MB) in Amazon Bedrock AgentCore agents, resulting in up to 71% token consumption reduction and 80% latency improvement.
  • Strategy 1 involves persisting lightweight session state and offloading large artifacts to Amazon S3 using content-addressed storage (SHA-256 hashing) and an in-process cache, accessible via the S3ArtifactStore class.

Best practices for writing Denied Topics in Amazon Bedrock Guardrails

Amazon Bedrock Guardrails’ Denied Topics feature allows blocking content categories using plain language, but can unintentionally block legitimate queries if not implemented carefully.

  • The feature blocks content based on meaning, not keywords, but broad topic definitions can over-block, while narrow definitions may miss intended targets.
  • Effective topic creation requires focusing on the user’s intention rather than the subject domain, using action-oriented names (e.g., “Investment Recommendations” instead of “Finance”).
  • Topic definitions should begin with an action (e.g., “Asking for…”) and specify concrete objects to narrow the scope, avoiding broad subject-area openers.
  • A recommended structure for definitions is: “[Action or content-type opener] for [specific objects] by [qualifying constraint or purpose]”. Each topic has a name (max 100 characters), a definition (100-300 characters ideal), and up to five examples (max 100 characters each).
