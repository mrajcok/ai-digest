Best practices for writing Denied Topics in Amazon Bedrock Guardrails

Amazon Bedrock Guardrails’ Denied Topics feature allows blocking content categories using plain language, but can unintentionally block legitimate queries if not implemented carefully.

  • The feature blocks content based on meaning, not keywords, but broad topic definitions can over-block, while narrow definitions may miss intended targets.
  • Effective topic creation requires focusing on the user’s intention rather than the subject domain, using action-oriented names (e.g., “Investment Recommendations” instead of “Finance”).
  • Topic definitions should begin with an action (e.g., “Asking for…”) and specify concrete objects to narrow the scope, avoiding broad subject-area openers.
  • A recommended structure for definitions is: “[Action or content-type opener] for [specific objects] by [qualifying constraint or purpose]”. Each topic has a name (max 100 characters), a definition (100-300 characters ideal), and up to five examples (max 100 characters each).

Taxonomy of multi-agent design patterns, anti-patterns, and lessons from manufacturing

  • This post details design patterns and anti-patterns for building multi-agent systems, framing coordination as a distributed systems problem where complexity often exceeds understanding.
  • Tier 1 patterns (Sequential Pipeline, Conditional Workflow, Conditional Router, Parallel Workflow) offer deterministic control flow, defined at build time, suitable for predictable tasks like ETL or document processing.
  • Tier 2 patterns (Plan-based orchestration, Handoff, Conversation-driven, Debate/consensus) allow the LLM to determine control flow at runtime, offering flexibility for tasks with undefined subtasks, but at the cost of increased latency and debugging complexity.
  • Common anti-patterns include “God agents” (too many tools per agent), unbounded iteration (no retry limits), natural-language contracts (lack of schema), premature multi-agent systems, and unguarded customer contact, all leading to increased costs and risks.

Four Amazon Bedrock inference choices that affect cost

Amazon Bedrock offers four inference choices – cache duration, service tier, reasoning effort, and maxTokens – impacting cost without altering the model or prompt.

  • Cache Duration: Supported Anthropic models and GPT-5.6 models offer 5-minute and 1-hour TTL (Time-To-Live) options for prompt caching, with rates impacting cost (e.g., 5-minute write costs 1.25x input rate for Anthropic Claude Sonnet 5). Longer durations are beneficial with frequent reuse, but require at least 2 requests within an hour to justify cost with a 1-hour cache.
  • Service Tier: Models supporting "Flex" offer a lower-cost option for latency-tolerant workloads, but requests to unsupported models will return a ValidationException. Nova 2 Lite and gpt-oss-120b currently support Flex, while Claude Sonnet 5 and Opus 5 do not.
  • Reasoning Effort: Claude Sonnet 5 and Opus 5 default to high adaptive thinking effort, impacting output token count. Effort levels (low, medium, high, xhigh, max) can be adjusted via output_config, with lower effort potentially reducing cost but risking accuracy.
  • maxTokens: Sets a limit on output tokens, preventing runaway costs from poorly formed prompts. Amazon Bedrock deducts input tokens plus maxTokens when a request starts; larger values reduce concurrency. It’s important to calibrate this per task, considering P95/P99 percentiles, and is capped in conjunction with adaptive thinking.
