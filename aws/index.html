Run production AI agents in n8n with Amazon Bedrock AgentCore harness

AWS has released the AgentCore harness, a platform for building and scaling AI agents, now accessible within n8n through a new open-source community node (@aws/n8n-nodes-agentcore, version 0.3).

  • The node enables building production-ready agents with persistent memory, tool access (like code interpreters and web browsers), and the ability to switch between model providers (Amazon Bedrock, OpenAI, Google Gemini, and LiteLLM) mid-conversation.
  • AgentCore harness manages the orchestration loop, tool calls, context windows, state, failure recovery and session isolation—reducing the need for custom infrastructure code. Agents are defined via configuration, allowing for flexibility and control.
  • Features like actor IDs allow for scoped memory per user, and agents can run privately within a VPC by configuring network settings in the n8n credential.
  • The node supports features like skills (pre-built instructions/scripts), custom containers and inline functions, and uses the same AWS credential pattern as existing n8n AWS nodes.

How we built an MCP bridge to give our AgentCore-hosted AI agent access to local MCP tools

  • Amazon Bedrock AgentCore now supports bridging to local tools via the Model Context Protocol (MCP) using a WebSocket and native messaging tunnel.
  • The architecture includes an AgentCore runtime (cloud-hosted Strands agent), a browser extension, a local MCP Bridge (FastMCP proxy), and a local MCP Server.
  • The bridge translates between native messaging (browser extension to local process) and MCP (JSON-RPC over stdio) allowing a remote agent to interact with local files and tools.
  • Key components rely on securing communication through presigned WebSocket URLs (5-minute expiry) and native messaging origin restriction, with recommendations for JWT authentication, payload signing and file system scoping for enhanced production security.

How LendingTree built a multi-agent mortgage assistant on Amazon Bedrock

LendingTree built a multi-agent mortgage assistant using Amazon Bedrock to provide tailored guidance throughout the home-buying process.

  • The assistant utilizes three AI agents – a Supervisor and two specialized workers (Education and Matching) – orchestrated via LangGraph and the Model Context Protocol (MCP).
  • The solution leverages Amazon Bedrock models, specifically Amazon Nova Pro for complex reasoning and Amazon Nova Lite for conversational responses, dynamically selecting between them to balance performance and cost.
  • Amazon Bedrock Guardrails and a custom safety classifier are employed for content filtering, PII redaction, and compliance with mortgage industry regulations.
  • Conversation memory is managed using a LangGraph PostgreSQL checkpointer on Amazon RDS, enabling persistent and contextual conversations across multiple turns and agent handoffs.

Introducing Web Search on Amazon Bedrock for foundation model grounding

  • Amazon Bedrock now includes Web Search, a server-side tool for grounding model responses in current web knowledge, eliminating the need for third-party web search integrations.
  • Web Search utilizes a multi-source grounding approach, combining a web index with a knowledge graph for factual accuracy and efficient retrieval using semantic snippet extraction.
  • Enabling Web Search is done through a single parameter in the OpenAI Responses API, requiring no vendor onboarding, API keys, or SDKs, and supports zero data egress by default.
  • Web Search is integrated with AWS CloudTrail for auditing, logging InvokeSearch and InvokeFetch calls without exposing query text, and is currently available in US regions (us-east-1, us-east-2, us-west-2).

Automated Reasoning policy refinement in Amazon Bedrock

  • Amazon Bedrock now offers automatic policy refinement to automate the process of diagnosing and fixing issues in Automated Reasoning policies, reducing manual effort.
  • Two new refinement modes are available: Iterative Refinement addresses rule issues by proposing edits to formal logic, while Ambiguous Variable Refinement resolves language issues by suggesting clearer variable descriptions.
  • Iterative Refinement requires a source document and optional feedback, analyzing divergence from the document to propose rule or variable changes, and uses an asynchronous API workflow (start, poll, retrieve).
  • Ambiguous Variable Refinement identifies overlapping or incomplete variable definitions causing translation issues and proposes refined descriptions, utilizing the same API workflow as Iterative Refinement but without the need for a source document or tests.
