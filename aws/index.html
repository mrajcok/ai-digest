Four Amazon Bedrock inference choices that affect cost

Amazon Bedrock offers four inference choices – cache duration, service tier, reasoning effort, and maxTokens – impacting cost without altering the model or prompt.

  • Cache Duration: Supported Anthropic models and GPT-5.6 models offer 5-minute and 1-hour TTL (Time-To-Live) options for prompt caching, with rates impacting cost (e.g., 5-minute write costs 1.25x input rate for Anthropic Claude Sonnet 5). Longer durations are beneficial with frequent reuse, but require at least 2 requests within an hour to justify cost with a 1-hour cache.
  • Service Tier: Models supporting "Flex" offer a lower-cost option for latency-tolerant workloads, but requests to unsupported models will return a ValidationException. Nova 2 Lite and gpt-oss-120b currently support Flex, while Claude Sonnet 5 and Opus 5 do not.
  • Reasoning Effort: Claude Sonnet 5 and Opus 5 default to high adaptive thinking effort, impacting output token count. Effort levels (low, medium, high, xhigh, max) can be adjusted via output_config, with lower effort potentially reducing cost but risking accuracy.
  • maxTokens: Sets a limit on output tokens, preventing runaway costs from poorly formed prompts. Amazon Bedrock deducts input tokens plus maxTokens when a request starts; larger values reduce concurrency. It’s important to calibrate this per task, considering P95/P99 percentiles, and is capped in conjunction with adaptive thinking.

Detecting and recovering from silent data corruption on Amazon SageMaker HyperPod

  • Amazon SageMaker HyperPod now includes three checks within a PyTorch DistributedDataParallel (DDP) training loop to detect silent data corruption (SDC), which occurs when hardware errors don't raise exceptions but introduce incorrect values into training.
  • The first check identifies non-finite gradients (NaN, Inf, overflow) before and after the all-reduce step. The second, a “ring replay audit,” recomputes micro-batches from other nodes to compare loss bits and gradient fingerprints. The third compares weight fingerprints after the optimizer step.
  • The solution utilizes Kubernetes and SageMaker HyperPod features to localize the issue to a specific node upon detection, cordon the node, and initiate replacement. This process leverages DCGM metrics and deep health checks for correlation and confirmation.
  • The checks require a SageMaker HyperPod cluster with at least three GPU nodes, a PyTorch DDP training job with a rebuildable data pipeline, checkpoints on shared storage, and access to observability tools and AWS IAM permissions for node management.

Semantic diffing of formal policies with anti-unification

AWS introduces a semantic diffing engine for formal policies using anti-unification to identify meaningful changes beyond syntactic differences.

  • The engine uses anti-unification to find the most specific common pattern between two policy expressions, revealing shared structure and pinpointing disagreements.
  • It operates on an e-graph, leveraging algebraic laws and domain rules to equate expressions, enabling comparison of policies despite variations in syntax.
  • A key use case is comparing formalizations generated by Large Language Models (LLMs) – running the model multiple times and using semantic diffing to review changes.
  • The engine can process policies written in SMT-LIB, Cedar, Dogwood, OpenShell, and CEL formats, identifying semantic differences despite variations in language syntax; it requires S-expression syntax familiarity and provides a command-line interface for use with a pinned Rust toolchain.
