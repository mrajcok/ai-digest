Anthropic blog · 2026-11-17

Using a "chaos loop" to harden the Claude Docs launch: 60 server errors across billions of requests / claude.dev Blog

Anthropic used a “chaos loop” powered by an internal Claude model (comparable to Claude Fable 5.2) to harden the launch of Claude Docs, a collaborative document editor. Prior to release, the model was set to proactively break the service in a staging environment, simulating high load and failure scenarios – including creating millions of synthetic documents and simulating reconnection spikes. The loop involved Claude reading telemetry, proposing fixes, and deploying them to staging for retesting, iterating continuously for two weeks.

Key to success was making the service “legible” to Claude: utilizing Rust to avoid unpredictable memory management inherent in garbage-collected runtimes, minimizing external dependencies, and generating detailed telemetry on every operation (database queries, memory usage). This allowed Claude to accurately diagnose issues and implement targeted solutions. The process resulted in only 60 server errors across 2 billion requests during the first week of launch despite estimates of millions of documents being created daily, and required roughly 50 memory-optimized pods. The total inference cost was approximately $125,000.

Google blog · 2026-11-19

Introducing Tool Retrieval in the Gemini API

  • The Gemini API introduces Tool Retrieval in preview within the Interactions API, aimed at improving agent scalability with large tool libraries.
  • Tool Retrieval reduces input token counts and latency by deferring the loading of tool parameter schemas until they are needed, activated by setting defer_loading: true for specific tools.
  • The feature utilizes a tool_search tool type to identify necessary schemas on demand, without requiring upfront loading of all tool details, shown in example code using the genai library.
  • Tool Retrieval is compatible with Gemini 3.6 and later models (including Gemini 4 variants) and does not incur separate charges, billed according to standard token usage rates; it also supports both server-side and client-side retrieval methods.

AWS blog · 2026-11-20

Use Kimi Code CLI with models on Amazon Bedrock

Kimi Code CLI v2.7.0 introduces a native provider for Amazon Bedrock, allowing authentication via existing AWS credentials.

  • The new provider utilizes the standard AWS credential chain, including named profiles and SSO, eliminating the need for separate Bedrock API keys.
  • The system uses @aws/bedrock-token-generator to create short-lived bearer tokens for authentication against Amazon Bedrock.
  • Configuration is done via config.toml, specifying the bedrock provider type, AWS Region, and model ID (e.g., global.moonshotai.kimi-k3.1).
  • Kimi K3.1 Pro Highspeed is used as an example, supporting features like streaming, configurable reasoning, and client-side tool calling, and requires appropriate IAM permissions for bedrock:CallWithBearerToken, bedrock:GetInferenceProfile, and bedrock:InvokeModel.

AWS blog · 2026-11-19

Using NVIDIA Run:ai GPU Fractioning on Amazon EKS

NVIDIA Run:ai GPU Fractioning on Amazon EKS enables sharing a single GPU between multiple Kubernetes Pods with enforced memory limits.

  • It builds upon NVIDIA's Multi-Process Service (MPS) with Kubernetes scheduling integration and per-Pod memory contracts.
  • The validated example uses an Amazon EC2 g5.xlarge instance with an NVIDIA A10G GPU and establishes 8 GiB memory contracts, allocating 6 GiB per Pod.
  • It utilizes the open-source NVIDIA Run:ai (KAI Scheduler and GPU Fractioning Operator v0.1.7, released October 13, 2026) and custom Amazon Linux 2023 images with NVIDIA driver 615.71.10.
  • GPU fractioning is suited for workloads like interactive notebooks, short evaluation jobs, and small inference services needing enforced per-Pod GPU-memory limits on GPUs lacking MIG capabilities.
